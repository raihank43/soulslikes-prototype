# Rethink — Tightening the Build Feedback Loop

_Date: 2026-06-21 · Scope: development workflow (not game architecture) · Mode: focused sweep, no count cap_

> **Goal of this rethink:** reduce the number of iterations needed to land each feature.
> **Read-and-propose only — nothing here changes code until triaged into PLAN and forged.**

---

## Why we iterated so much (root-cause read of the build journal)

Reading Days 0 → 4.5 back-to-back, the gotchas cluster into **four feedback-gap categories**. Almost none of them were "the gameplay logic was wrong." They were **things neither of us could see until a playtest exposed them:**

| # | Category | Representative gotchas | Who caught it today | Cost |
|---|----------|------------------------|---------------------|------|
| 1 | **Silent asset-import resets** | FBX reimport flips `useFileScale` (100× scale → 242 m/s), wipes `clipAnimations` loop flags, orphans `BlendTree.children[].motion` refs, inflates `clip.length` 2.6×/pass | Read-back of importer state, or a playtest | Highest — hit on Days 0,1,2,3,4,4.5 |
| 2 | **Silent animation-event / timing failures** | Events past `exitTime` dropped; event-name typos = silent no-op; `normalizedTime` unreliable on inflated clips; controller cached at Play start | Playtest ("hitbox never fires") | High |
| 3 | **Invisible visual/feel bugs** | Ice-skating, floating feet, spin-on-idle, treadmill, glide-out-of-roar | **Only the user, by watching** | High — full human round-trip every time |
| 4 | **Logic / balance correctness** | Damage values, stamina gating, per-attack cooldown throttle, distance bands, combo chains | Playtest | Medium — but no regression net |

**The thesis:** every category above is a *loop I currently can't close without you*. The proposals below close them — in priority order of how much iteration they remove.

### Web-dev Rosetta (so the Unity terms map to what you know)

| Unity thing | Your web-dev equivalent |
|-------------|------------------------|
| EditMode test | unit test (no scene, pure logic) |
| PlayMode test | integration / e2e test (real scene, real frames) |
| `execute_code` (MCP) | a REPL / `node -e` against the running app |
| `ScreenCapture` + I `Read` the PNG | Playwright screenshot / visual-regression snapshot |
| Runtime telemetry log | structured logging / observability |
| Seeded RNG + manual clock | deterministic test fixtures / fake timers |

## Proposals (impact-ranked)

### P1 — PlayMode "combat invariants" test suite  ⟶ kills category #4, nets regressions
**Altitude:** implementation · **Confidence:** high-confidence win · **Serves:** every row in PLAN's Decisions Log

Stand up `Assets/_Project/Tests/` (PlayMode asmdef referencing the gameplay asmdef — which P0-prereq below adds) with a small harness that loads `SampleScene`, positions player + mutant at a chosen range, drives one action, and **asserts numeric outcomes:**

- Light1 deals exactly 18 to `EnemyHealth`; Light2=22, Light3=32, Heavy=45 (the Day 3 damage table).
- Insufficient stamina ⇒ press is consumed, **no** HP change, **no** chain advance (Day 3 stamina-gate intent).
- Enemy at 1.4 m picks Punch; at 2.6 m Swipe; at 5 m with jump off-cooldown leaps, on-cooldown stays in Chase (Day 4.5 distance bands + jump cooldown).
- Combo chain never exceeds `comboMaxLength`.
- **Day 5 i-frames (the headline):** damage applied during the roll's invuln window ⇒ HP unchanged; same hit one frame after the window ⇒ HP drops. *This feature is genuinely hard to ship with confidence without this test — it's a binary, numeric, perfectly testable property.*

I run these via MCP `run_tests` and self-check before pinging you. **Each Decisions-Log entry becomes an executable invariant** — that's the regression net we don't have.

**Respects the fence:** tests assert *observable outcomes* (HP, position, i-frame), **not** Animator graph internals — the "Animator IS the state machine, no script counter" decision stays intact.

---

### P2 — Asset-import verifier  ⟶ kills category #1, likely highest ROI
**Altitude:** implementation · **Confidence:** high-confidence win · **Serves:** the FBX-repair recipe that recurs Days 0–4.5

A reusable EditMode test + editor utility that, given an FBX path, asserts the things that silently reset on reimport:

- `animationType == Humanoid`, avatar present (not `NoAvatar`/Generic).
- `useFileScale == true` **and** `apparentSpeed` within a sane band (catches the 100× scale → 242 m/s bug immediately).
- Each clip's `loopTime` matches an expected manifest; `lockRoot*` flags as configured.
- `clip.length` not inflated beyond the true take length (catches the 2.6×/pass balloon).
- **No null/orphaned `BlendTree.children[].motion` refs** in `MutantAI`/`PlayerLocomotion` controllers (catches the fileID-orphan bug).

Run after *any* reimport or FBX swap. This is the single biggest iteration sink across the whole journal, and it's the most mechanical to catch — which is exactly why automating it pays back fastest.

**Respects the fence:** encodes the existing FBX-repair recipe (Humanoid + CopyFromOther/CreateFromThisModel + `useFileScale` + loop flags + relink motions) as an *assertion*, not a new workflow.

---

### P3 — Screenshot-based visual verification  ⟶ kills category #3, the "playtest directly" answer
**Altitude:** implementation · **Confidence:** high-confidence the capability exists; the workflow is new · **Serves:** every feel-bug that previously required a human watch

The loop: `execute_code` poses the scene (e.g. sample an attack clip at `normalizedTime` 0.2 / 0.5 / 0.8, or enter Play and step) → `ScreenCapture.CaptureScreenshot(temp.png)` → I `Read` the PNG and **see** it. Combined with telemetry (P4), I can check "is the foot on the ground at the strike frame," "is the sword arc where the hitbox is," "did the body translate or ice-skate" — **without you watching.**

**Honest caveat (this is the boundary):** I get **sampled frames + numbers**, not a 60 fps video of *feel*. Perceptual judgments — "does the dodge feel snappy," "is the cadence right" — still need your eyes. This converts *most* feel bugs (geometry, grounding, position) into things I catch myself, and narrows what I escalate to you to genuinely subjective calls. Worth a 10-minute spike to prove the capture→Read path end-to-end before we lean on it.

---

### P4 — Runtime combat telemetry  ⟶ makes categories #2 & #3 self-diagnosable
**Altitude:** implementation · **Confidence:** high-confidence win · **Serves:** the silent-failure gotchas (dropped events, typo'd event names)

A `CombatTelemetry` component (events-based, subscribes to the same `HealthChanged`/`Died`/hitbox signals — no singletons) that emits **structured** records: damage dealt/taken with values, attack-state entered/exited, hitbox open/close windows, i-frame windows, and a foot-speed-vs-body-speed ratio sample. After any play session (manual or P5-scripted), I read the log and verify the loop numerically — a dropped `EnableHitbox` event shows up as "swing with no hitbox-open record" instead of a mystery.

Formalizes the ad-hoc `combat_log.txt` that already exists. **Keep the artifact git-ignored** (RULES already says don't commit `combat_log.txt`).

---

### P5 — A `/playtest` project skill  ⟶ ties P1/P3/P4 into one repeatable command
**Altitude:** feature-design (of the workflow) · **Confidence:** medium · **Serves:** making the above loops cheap enough to actually run every change

A documented, repeatable procedure that: enters Play → drives a scripted scenario via `execute_code` (spawn at range X, force enemy attack Y, roll on frame Z) → captures screenshots + telemetry at key frames → asserts → exits Play. Encodes the workflow so it's one invocation instead of re-derived each session. Generic `verify`/`run` skills exist; this is the project-specialized version that knows our scene, our components, our ranges.

*Lower confidence only because its value depends on P1/P3/P4 existing first — it's the orchestration layer, build it last.*

---

### P6 — Deterministic combat-sim mode  ⟶ speculative bet; makes P1/P3 reproducible
**Altitude:** architecture · **Confidence:** speculative bet · **Serves:** test reliability for P1

The AI uses `Random`/`WeightedPick` and `Time`-based coroutine waits — non-deterministic, which will make P1's range-band and combo tests **flaky**. Injecting a seedable RNG (an `IRandom` the AI reads instead of `UnityEngine.Random`) and a test-controllable clock makes the combat loop reproducible frame-for-frame, so a failing test means a real regression, not a dice roll.

**Why it's a bet, not a win:** it's a real refactor with surface area across `EnemyAI`/`EnemyAttack`, touching shipped code for a test-only benefit. Worth it *if* P1's tests prove flaky; premature otherwise. Recommend: build P1 first, adopt P6 only if/when flakiness actually bites.

## Explicitly NOT proposing (preserved negative space)

- **Don't assert "feel" thresholds in tests.** Treadmill/ice-skating/cadence are perceptual; they belong to P3 screenshots + your eyes, not a numeric gate. Encoding a "foot-speed ratio must be 0.75" assertion would calcify a tuning value that was deliberately dialed by feel.
- **Don't add a script-side combo/state counter to "make it testable."** The "Animator IS the state machine" decision is load-bearing (avoids dual-source-of-truth). Tests observe outcomes instead.
- **Don't re-introduce `normalizedTime`/animation-event-driven completion** anywhere in the harness — the FBX clip-length inflation gotcha killed that on Day 4.5. Harness uses absolute-time / `DurationFor` like the shipped code.
- **Don't reach for a third-party test/automation asset.** Everything needed (Test Framework, Performance Testing, ScreenCapture, MCP) is already installed — adding a dependency would be the generic-best-practice trap RULES warns against.

## Suggested sequencing

A **prerequisite P0** underlies P1/P2: split first-party scripts into a `Soulslike` runtime asmdef so a `Tests` asmdef can reference them (right now there's no asmdef, so everything is in `Assembly-CSharp` and tests can't cleanly target it). Small, mechanical, unblocks everything.

1. **P0** asmdef split (prereq).
2. **P2** import verifier — fastest payback, attacks the #1 sink, useful immediately.
3. **P1** combat invariants — land it **with Day 5** so i-frames ship tested, then backfill Day 3/4/4.5 invariants.
4. **P3 + P4** screenshot + telemetry — the "I can see it" pair.
5. **P5** `/playtest` skill — orchestration, once the pieces exist.
6. **P6** determinism — only if P1 proves flaky.
